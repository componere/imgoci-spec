## 2026-08-10 14:48 — Incus support analysis
Goal clarified: Add Incus support before the first imgoci release, covering the split VM image shape and optionally a logical SimpleStreams compatibility check.
Current findings: imgoci already models standalone QCOW2 but not Incus's coordinated metadata-plus-disk deliverable. Incus supports unified and split images; the split VM form is a metadata tarball plus a QCOW2 disk and is the better fit for a multi-consumer format. Incus's SimpleStreams client expects catalog metadata plus either a unified image or the split `incus.tar.xz` and `disk-kvm.img` pair, with an image fingerprint over the concatenated metadata and disk bytes.
Recommended direction: Add public `incus` target and `incus-vm` coordinated representation values with required `metadata` and `disk` roles. Keep SimpleStreams out of the core OCI object model; define an optional projection/validation profile that checks architecture mapping, metadata fields, transport availability, hashes, sizes, and the combined fingerprint. Prove the shape with one real image and Incus import/launch before finalizing normative prose and CUE constraints. Release PR #3 is still open and should remain unmerged until this work lands.

## 2026-08-10 14:54 — SimpleStreams boundary clarified
Decision: Do not name or encode SimpleStreams support, compatibility, profiles, or dependencies in the imgoci specification. Treat it only as a one-time design assertion that an Incus imgoci deliverable contains enough information to materialize a working SimpleStreams catalog without changing the release model.
Proof boundary: A disposable projection may map architecture names, read the Incus metadata payload, compute per-file and combined fingerprints, and supply catalog policy such as aliases externally. If the proof exposes missing image facts, fix the Incus representation; do not add SimpleStreams concepts merely to mirror its catalog schema.

## 2026-08-10 14:57 — Proposed execution sequence
Approach: Work evidence-first in four small slices. First, build a disposable projection from one provisional imgoci release containing a real Incus metadata archive and QCOW2 disk, then prove Incus can list, import, and launch it through a generated catalog. Second, use only the facts exposed by that proof to define the minimal normative `incus` target and coordinated representation. Third, add focused CUE required-role constraints plus positive and negative conformance cases, leaving payload inspection to the full validator. Fourth, rerun the real Incus proof, local and hosted repository gates, and only then allow the first release to proceed.
Stop condition for the spike: Report before normative edits if materialization requires inventing intrinsic image data, changing the imgoci object model, or adding SimpleStreams-specific fields. Mechanical translation, hashing, recompression, and externally supplied catalog policy do not count as model gaps.

## 2026-08-10 15:23 — Slice 1 Incus projection proved
Environment: Created only the disposable Lima instance `imgoci-incus-spike` on an Apple M4 Max host. Lima 2.0.3 used VZ with nested virtualization enabled; the Ubuntu 24.04 ARM64 guest exposed `/dev/kvm`. Installed Incus 6.0.0 and QEMU 8.2.2. Ubuntu's Incus package expected `OVMF_CODE.fd` and `OVMF_VARS.fd`, while the ARM firmware package supplied the equivalent `AAVMF_*` names, so the disposable guest used two compatibility symlinks before the QEMU driver became operational.
Baseline: Pulled the public Alpine 3.21 ARM64 virtual-machine image, launched it with its declared `security.secureboot=false` requirement, and received `uname` through the Incus VM agent. Exported the cached image as a 908-byte metadata archive and a 67,028,480-byte standalone QCOW2. Their SHA-256 digests were `9d5a4ab404ec2916079a74b632d8c4f24799339789d6a21914cd84bc1ecc494a` and `6f8bd7b5feda40e5078fd2c6493e6310cf5ff3a96bcb92e3ad173032a53c6028`; Incus's combined fingerprint was `a8c881d6b7ac5cde533f97f5163683a13338b7ddd98cd11a16f2ecf7886331f8`.
OCI proof: Ran a local CNCF Distribution registry and pushed both files with the BigOCI reference CLI from the current `componere/bigoci` checkout. The QCOW2 was intentionally split into four 16 MiB parts. Published a provisional, canonical imgoci release index at `127.0.0.1:5000/imgoci/alpine:release-1`, digest `sha256:6629d77b1bf85bf527e17917cc4b01c9961b4f5bb49d755ca59826682643f797`. It used the existing `arm64/qemu/qcow2` selectors, public `disk`, and private `x-componere-incus-metadata`, all with `compression=none`. The exact bytes passed the repository's CUE schema and a canonical JSON byte comparison.
Projection proof: A disposable standard-library Python script fetched the release index, selected the two roles, pulled each BigOCI manifest by digest, verified each decoded content size and digest, and passed the recovered pair to `incus-simplestreams add`. The generated catalog passed `incus-simplestreams verify` and contained the same combined fingerprint without inventing intrinsic image facts. Catalog naming and aliases came from the Incus metadata/tooling, outside imgoci.
End-to-end result: Served the catalog locally over HTTPS, added it as an Incus image remote, and confirmed `incus image list` exposed one 63.92 MiB ARM64 virtual-machine image at fingerprint `a8c881d6b7ac`. Deleted both the baseline instance and cached image before the final test. Incus then fetched metadata and disk from the projected catalog, recreated the expected local fingerprint, launched `imgoci-projected` in `RUNNING` state, and its agent returned Alpine Linux 6.12.98 on aarch64.
Design learning: The current object model can carry and faithfully project the Incus pair, so no SimpleStreams dependency or catalog fields are needed. However, `qcow2` currently requires only `disk`; default resolution therefore omits the extra metadata role. The next normative slice should add a coordinated Incus representation with public `metadata` and `disk` roles (and decide the narrowly named target) so a conforming consumer selects the complete pair without private knowledge.
